# TPRO on Base - snapshot table, merkle claim, claim page

Everything a holder, a partner or an auditor needs to check the migration of TPRO from
Ethereum and Polygon to Base, reproduce the published snapshot table and verify a claim:

| Path | What it is |
|---|---|
| `contracts/TPRO.sol` | The new TPRO token: OpenZeppelin v5.7.0 `ERC20 + ERC20Burnable + ERC20Permit`, nothing else. No owner, no mint, no pause, no fees, no hooks, no proxy. The whole genesis is minted once, to the distributor. |
| `contracts/TPROMerkleDistributor.sol` | Immutable and keyless. `claim(account, amount, proof)` pays one row of the published table, once, to the address itself (`msg.sender == account`). After the claim window anyone can call `sunset()`, which burns the remainder. No owner, no pause, no upgrade, no rescue function. |
| `script/DeployV3.s.sol` | Published at launch together with the verified deployment (until then the repository carries the contracts, the tool, the page and the tests). The deployment: token and distributor in one run; the distributor through CREATE2 (its address does not depend on the deployer's nonce), with the wiring proven by the distributor's own balance. The script refuses a table that is not the published, validated one. |
| `scripts/snapshot/` | The snapshot tool. Reproduces the table from public archive nodes: every holder of the original token at the pinned Ethereum block plus the Polygon block at the same timestamp, staking and vesting balances credited to their owners, one row per address, exclusions per the published rules, the merkle root and the proof shards. See `scripts/snapshot/README.md`. |
| `website/` | The claim page (two files, zero external dependencies) and `verify_deploy.mjs`, the gate run before every publication. See `website/README.md`. |
| `docs/v3-interface.md` | The shared specification: contract ABI and selectors, the table format, the claim-page rules, the deployment sequence. |
| `test/` | Foundry tests: unit, fuzz, invariant, known-answer fixtures generated by the Python tool and cross-checked with the OpenZeppelin JavaScript merkle library; the deploy-script tests join at launch with the script. |
| `AUDIT.md` | The review history: the builder's passes, the independent review rounds, the external read-only review, and the disposition of every finding. |

The published table (CSV, `index.json`, proof shards, `SHA256SUMS`) is served next to the
claim page. `index.json` carries the merkle root, the two pinned block numbers with their
hashes, the CSV sha256 and the exact commit of the tool that produced it; the announcement
links the page and this repository. The reproduction command is below.

## Reproduce the published table

```bash
git clone --recurse-submodules https://github.com/TPRO-Network/tpro-token && cd tpro-token
python3.12 -m venv .venv && .venv/bin/pip install -r scripts/snapshot/requirements.lock
export ETHERSCAN_API_KEY=...            # a free Etherscan API v2 key (Ethereum + Polygon logs / ABIs)
export ETH_ARCHIVE_RPC=https://...      # an Ethereum ARCHIVE endpoint (a free Alchemy or dRPC key)
export POLYGON_ARCHIVE_RPC=https://...  # a Polygon ARCHIVE endpoint
.venv/bin/python scripts/snapshot/snapshot.py --at-utc <the announced instant> --eth-block <N> --polygon-block <M> --workers 4
```
The run prints the merkle root, the CSV sha256 and a deterministic "content sha256"; compare
them with the announcement and with `index.json`. The method, every assertion the tool makes
and the exclusion rules are in `scripts/snapshot/README.md`.

## Verify a row and the root without the tool

```js
// Node: npm i @openzeppelin/merkle-tree  (the reference implementation of the tree format)
import { StandardMerkleTree } from "@openzeppelin/merkle-tree";
const rows = /* the published CSV as [address, amount_wei] pairs */;
StandardMerkleTree.of(rows, ["address", "uint256"]).root   // == index.json merkleRoot == distributor.merkleRoot()
```
Leaf = `keccak256(keccak256(abi.encode(address, uint256)))`, sorted pairs. A proof from the
shard `proofs/<first two hex chars of the lowercase address>.json` walks to the root; the
contract checks exactly that.

## Claim without the page

`claim(address account, uint256 amount, bytes32[] proof)` on the distributor, sent BY the
account itself, value 0. Selector `0x3d13f874`. Any explorer's "write contract" form or `cast
send` works; the page's "Claim without this page" box prints the exact arguments and calldata.

## Run the checks

```bash
forge test                                                       # contracts, known-answer fixtures (the deploy-script tests join at launch)
.venv/bin/python scripts/snapshot/selftest.py                    # the tool's offline guard checks
node website/verify_deploy.mjs website --table ./table-sample/   # the claim-page gate on the sample table
```
This repository carries no workflows or automation; the checks are meant to be run by the reader.
Verified with Foundry 1.5.1, 1.7.1 and 1.8.1: `foundry.toml` pins the classic test mode, and the
suite also passes with Foundry 1.8's isolated mode and dynamic test linking switched on (1.8
prints the six invariant predicates as one campaign, so its summary line reads 43 tests).

## Security

The token and the distributor hold no keys and have no privileged functions. The page loads
no external code, verifies the served table against pinned checksums and the on-chain root,
and describes the one legitimate wallet prompt before every claim (to = the distributor, 0
ETH, Base, one transaction, never a signature or approval). Report anything that looks wrong
through the official community channel named in the announcement, never through links sent
to you in private messages.
